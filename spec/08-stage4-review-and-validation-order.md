# 08 段階4の結果の検討と、今後の検証の順序

2026-10-05。spec/07（Agent Procurement Policy Engine）段階4の結果を受けた、オーナーからの検討依頼、
Claude Code の分析、オーナーの判断、そして次に同じ失敗をしないための検証の順序の記録。

## 1. 依頼（オーナーより、要旨）

段階4で Spend Guard の必要性判定が成立しなかった。続けるか、形を変えるか、止めるかを、根拠とともに提案すること。
実装の指示ではない。段階5には進まない。しきい値を `validated: true` にしない。他のプロダクト
（MAP / CONSUME / PRODUCE）の進め方には踏み込まない。実データを使う場合は依頼の形で書く。

段階4の結果（devnet 48件、境界 0.30〜0.85 の25件、必要12・不要10・わからない3）:

```
necessity ("necessary or useful")  必要 0.30 / 0.72 / 0.84   不要 0.37 / 0.74 / 0.84   (min / median / max)
necessity ("necessary")            必要 0.12 / 0.38 / 0.68   不要 0.19 / 0.44 / 0.71
nature                             必要 direct 9 / supporting 3   不要 direct 7 / supporting 3
duplicate                          必要 0.05 / 0.07 / 0.90   不要 0.06 / 0.07 / 0.93
flagged→unneeded                   どのしきい値でも 40〜47%（不要の構成比 10/22 = 45% と同じ）
```

## 2. 判定: Jev の限界か、検証設計の失敗か、問いの立て方か

**主に検証設計の失敗、次に問いの立て方。Jev の限界は、このデータでは判定できない。**

### 根拠

1. **境界に絞ったことで、Jev が効く領域を外した。**
   境界25件の nature は direct と supporting だけで、unrelated が1件もない。シナリオには明らかに無関係な購入が
   少なくとも7件ある（動画に weather-tokyo、会場予約に crypto-price-feed、翻訳に holiday-calendar と
   clip-beach-day、ETH 価格に weather-tokyo、税務に music-track、週次レポートに clip-city-night）。
   段階2の実測では無関係な購入は necessity 0.02、unrelated 1.0 と明確に分かれていた。それらは 0.30 未満として
   除外されたと推測される（5節の確認で確かめる）。「信号があると分かった後にしきい値を詰める方法」を、
   最初の検証に使ってしまった。境界だけのモードを実装したとき、「両端の性能は測れない」とは書いたが、
   「この設計では Jev が効くかどうか自体に答えられない」とは明言しなかった（Claude Code の落ち度）。
2. **「不要」のラベルに、necessity では捉えられない理由が混ざっている。**
   シナリオには同じ URL の2回目が6件ある。品物自体はタスクに関係しているので necessity が高いのは正しく、
   不要な理由は重複（duplicate の役割）。2回目を「不要」として necessity で採点したため、問いと正解がずれた。
3. **件数が足りない。** 必要12・不要10では、AUC の95%信頼区間がおよそ 0.25〜0.75（Hanley–McNeil 近似）。
   中程度の信号の有無も言えない。
4. **ラベルの揺れ。** 架空のタスクと売り手で、オーナーにとって実感のない購買だった。1回目の無作為なラベル付けの際、
   ラベルの後に Jev の答えが表示されていたので、2回目に影響した可能性がある（向きは不明）。
5. **問いの立て方。** 境界の購入の必要・不要を分ける情報（エージェントがすでに持っているもの、他で無料か、計画上の役割、
   過剰か）は state にない。state にあるのは目的と、利害のある売り手が書いた説明。入力にない情報は、どのモデルでも当たらない。

### 購入前と購入後の差は構造的か

構造的と考える。

- **Delivery Review は照合。** 要求と応答の両方が入力にあり、正解は渡したデータの性質として決まる。
- **Spend Guard の necessity は予測。** 入力にないオーナーの意図を当てることになり、主な材料が売り手の説明になる
  （原則5「売り手の主張を根拠にしない」と緊張関係にある）。
- **合成データでの検証の成否も違う。** Delivery Review は欠陥を作り込んだ合成データでも、正解が作り方から決まるので
  検証が成立する。Spend Guard は成立しない。

ただし Delivery Review も未検証。段階3の3件は極端な例で、3件ともコードの検査（`fields_ok`）だけで捕まっている。
Jev がコードの検査に何を足すかは、まだ示されていない。

## 3. 推奨と、推奨しないもの

推奨:

1. **Spend Guard の「必要か」は、この形では判定に入れない。** 5節の確認の結果で、「無関係な購入の検出」に絞るか、
   記録を残して閉じるかを決める。
2. **重複はコードで判定する。** 同じタスクで同じ URL の再購入は、URL の一致と既存の再購入ルールで判定できる。
   実害が出たのは処理中の購入の二重払いで、これはモデルではなく8節（予約・確定・解放）の問題。
   Jev の duplicate に意味があるのは「URL が違って中身が同じ」購入だけで、そこは未検証。
3. **Delivery Review を軸に据え直す。** 作り込む前に、コードの検査は通るのに中身がおかしい難しい例で、
   Jev が `fields_ok` に何を足すかを確かめる。足さなければ、コードだけで動かす。
4. **実データでの検証は Delivery Review のために依頼する**（6節）。

推奨しない:

| 選択肢 | 理由 |
|---|---|
| D 今 Clef を試す | state にない情報はモデルを変えても当たらない。22件ではモデルの差が信頼区間に埋もれる。切り替えと聞き直しは実装済みなので、有効な検証用データができた時点で数分で比べられる |
| A を Jev で実装 | 完全な重複はコードの方が確実で、遅延も外部送信もない。意味上の重複は未検証 |
| C を架空の題材でやり直す | 主観ラベル × 架空の購買という形自体が問題なので、同じ失敗を繰り返す |
| E 全体を閉じる | 早すぎる。Delivery Review は未検証で、二重払いの欠陥は実害として確認済み |
| Spend Guard を shadow で回し続ける | 使わない判定のために、購入のたびに目的と売り手の説明を外部へ送る |

## 4. 検証の順序（次に同じ失敗をしないために）

モデルの判断を使う機能は、層を作る前に次の順で確かめる。

1. **成功と中止の基準を先に書く。** 例: 「AUC の95%信頼区間の下限が 0.65 以上で、コードだけの方法を上回る」。
   満たさなければ止める、と書いておく。
2. **30〜50件の例に、モデルを回す前にラベルを付ける。**
   - 例を作った人とラベルを付ける人を分ける。または、正解が作り方で決まる例にする。
   - 両端の例も含める。境界に絞るのは、信号があると分かった後のしきい値の調整のときだけ。
   - ラベルが何を意味するかを問いと揃える（例: 重複は「不要」ではなく「重複」として別に付ける）。
3. **層を作らず、生の API を1本のスクリプトで回す。** 呼び出し層、記録、ゲートへの組み込みはまだ作らない。
4. **コードだけの方法と並べて採点する。** URL の一致、`fields_ok` など、モデルなしで出せる基準線と比べ、
   モデルが何を足すかを見る。
5. **基準を満たしたものだけに、層を作る。**

今回これを先にやっていれば、1日で分かった。spec/07 の実装順（1〜8）より先に、Claude Code から
「先に検証を」と提案すべきだった。

## 5. 次の1手（オーナー承認済み、2026-10-05）

**確認すること:** 48件全体で、Jev が無関係な購入と重複を見分けているか。
これで、今回の失敗が「境界に絞ったことと重複の混入」によるのか、「Jev の限界」なのかが分かる。

```
npm run appe-label      境界から外れた23件にラベルを付ける（両端なので迷わないはず）
npm run appe-metrics    全48件で集計（unrelated=block の規則の行、ラベルごとの nature の内訳）
```

加えて、不要の内訳（重複 / 無関係 / 過剰 / 他で無料）を出力から読む。

**判定基準（事前に固定）:**

- nature=unrelated または低い necessity が、不要（無関係）を高い精度で拾い（目安: 拾ったもののうち8割以上が不要）、
  必要なものをほぼ止めていない → 失敗は検証設計によるもの。Spend Guard は「無関係な購入の検出」に絞る候補として残す。
  ただし、実運用でそうした購入がどれだけ起きるかは別途確かめる。
- 両端でも分かれない → Jev の限界。Spend Guard の necessity を閉じる。

**時間と費用:** オーナーの作業 20〜30分。Jev の新しい呼び出しはなく 0円。コードは書かない。

**Spend Guard の `mode` を `off` にするか**は、全48件の集計を見てからオーナーが決める。

その次（承認があれば）: Delivery Review の難しい例を30〜40件作り、Jev とコードだけの方法で比べる。
正解は作り方で決まる。作成に半日、実行は数分、Jev の費用は約 $0.001。

## 6. 依頼文の案（実データ。送るかどうかはオーナーが決める）

> x402 Autonomous Agent の購入記録を、Delivery Review（購入後の応答の検証）の評価に使わせていただけないでしょうか。
>
> - **目的:** 実際の売り手の応答で、コードの検査と判断モデルが不良な納品をどれだけ見分けるかを測ること。製品の判定には使いません。
> - **希望するもの:** 各購入のルート、売り手（週次の外部の第三者の売り手を含む）、時刻、HTTP ステータス、
>   応答本文または不良と分かった記録（空、古い、形式違いなど）。
> - **扱い:** 鍵や署名は不要です。本文は検証の環境内だけで扱い、台帳には残しません。
> - **お願いしたいこと:** 可能な範囲と形式を教えてください。

実データが最も役に立つのは Spend Guard ではなく Delivery Review。定時に決まったルートを買う運用では「必要か」は
ほぼ自明だが、実際の売り手が返す空・古い・形式変更・エラーの応答は、Delivery Review の検証に必要な材料になる。

## 7. 二重払いの修正（モデルの検証とは切り離す、オーナー承認済み）

2026-10-05 の段階4の実行で、処理中の支払いを再試行した結果、2件が二重に支払われた。モデルの検証とは独立した欠陥として、
先に直した（spec/07 8節の予約・確定・解放のうち、同一購入の部分）。

- 予約: 支払いの前に `payment_reserved` を台帳に記録する。確認と予約の間に await を挟まないので、
  同じプロセス内の2つの要求が両方通ることはない。
- 処理中の同じ購入（同じタスク、同じリソース）への再要求: `PURCHASE_IN_FLIGHT` で止める。
- 判断を始めた後に、同じ購入が完了していた場合: 予約の時点で `PURCHASED_SINCE_DECISION` として止める。
- 結果が分からない支払い（引き出しが時間内に確認できない、売り手から応答がない）: 予約を保持し、
  `PREVIOUS_PAYMENT_UNCONFIRMED` で止める。オーナーがチェーンを確かめてから
  `npm run task -- release <decision_id> --reason "..."` で解除する。解除と理由は台帳に残る。
- まだ範囲外: 複数のサーバープロセスにまたがる同時実行（ファイルの台帳では排他にならない）。
  結果不明の引き出しが実際に着金していた場合、その額はゲートの口座に残る（照合の仕組みはない）。

## 8. ラベルの一括適用（2026-10-06、オーナー承認）

残りのラベルは、オーナーの対応表（タスク × 品目）から機械的に決まる。4節の手順2の「作り方から正解が決まるラベル」に
当たるので、1件ずつ押さずに `npm run appe-label -- --from-file config/appe-labels.json` で適用する。

- 台帳には `owner_label` ではなく `rule_label` として残す。対応表そのもの（根拠の文、表、ハッシュ）は `rule_label_set` に1回記録し、
  各 `rule_label` はそのハッシュを持つ。集計では同じに扱い、`appe-metrics` は人の押したものと表から付けたものの件数を分けて出す。
- オーナーが押したラベルは上書きしない。表と食い違うものは一覧に出すだけ。
- 前回の境界ラベル（2回目を「不要」にした指示で付けたもの）は問いと正解がずれているので、オーナーは表に合わせると決めた
  （2026-10-06）。1件ずつ押し直さず、`--withdraw-conflicts --reason "..."` で食い違う分をまとめて取り下げる。
  取り下げは1件ずつ `owner_label_withdrawn`（元のラベルと理由）として残り、その後に表のラベルが付く。後からオーナーが押せば、それが再び優先される。
- 表にない品目はラベルなしのまま残し、一覧に出す。ETH価格タスクの crypto-news は、オーナーの判断で不要として表に追加した。

## 9. 段階4の結論と段階5（2026-10-06、オーナー承認）

全48件の集計（オーナーの Mac、jev-1.13.0）で、5節の判定基準を満たした。

```
necessary or useful   必要 0.61 / 0.80 / 0.90   不要 0.03 / 0.07 / 0.75   (min / median / max)
nature                必要 direct 19 / supporting 4   不要 unrelated 12 / supporting 9 / direct 1

necessary/useful block<0.20 ask<0.50 dup off unrelated=block   拾った不要 100% / 不要の捕捉 95% / 必要を止めた 0% / 確認 5件
necessary/useful block<0.40 ask<0.50 dup off unrelated=block   100% / 95% / 0% / 確認 0件
```

- 境界だけでは分離しなかったのは、境界に絞ったことと、重複を「不要」としたラベルのずれが原因だった（2節の判定どおり）。
- 重複の条件（duplicate >= 0.50）を入れた規則は 77% だった。増えた6件は、表で「品物としては必要」とした2回目の購入。
  5節の基準は necessity と nature についてのものなので、重複の条件なしで判定した。重複は再購入ルールに任せる。
- 見逃した1件: #13 music-track（動画タスク、or useful 0.75、nature direct）。楽曲が既にあることは目的文にない。
  2節の点5（入力にない情報）による、想定内の見逃し。無関係な購入は12件すべて拾った。
- 確かめた範囲: 架空のシナリオで、明らかに場違いな購入を見分けられるところまで。実際の購入での微妙な判断は未検証。
  表も Jev も同じ表面情報（目的と品名）から判断している。
- 誤って止める率の上限: 約13%（必要23件で0件、95%信頼度）。

決定（`config/appe-thresholds.json` の `validation` に記録、`validated: true`）:

- 問いは「必要または有用か」（別の呼び出しで、検証と同じ形）。確認の線 0.50、nature=unrelated は対象、重複の問いは使わない。
- 段階5は確認のみ（`spend_guard.mode: "confirm"`）。Spend Guard が止めるまたは確認とした購入は、オーナーの確認（World ID）に回す。
  Spend Guard は購入を止めない。固定ルールより緩くしない（BLOCK は BLOCK のまま）。答えられなければ確認に回す（設定が読めない場合も）。
- 0.20 は将来の自動停止の線として記録するだけ。自動停止は、確認モードで溜まる実際のラベル（`owner_decision_label`）か実データで
  同じ結果が出てから。
- オーナーの承認・拒否は `owner_decision_label`（承認=必要、拒否=不要、他の理由も添える）として台帳に残る。
  確認に回った購入にしか付かないので、測れるのは「確認が正しかったか」であり、「見逃し」ではない。

## 10. 固定ルールのベースラインと、継続の判断（2026-10-07、オーナー決定）

4節の手順4（コードだけの方法と並べる）を、段階5の後になって実施した。本来は段階4の前に済ませるべきだった。

### キーワードのベースライン（`npm run appe-keyword-baseline`）

ルールは採点の前に `scripts/appe-keyword-baseline.ts` に固定した。ただし、品目と説明はそれまでの作業で見ていたので、
データを見ずに決めたルールではない。同義語の辞書や、品目に合わせた語の一覧は使っていない。

- K1: タスクの目的と「品名＋売り手の説明」に共通する内容語がなければ確認に回す
- K2: K1 と同じで、品名だけと照合する

設定から再現できる40件（シナリオ34件と、それ以前の実行の6件。必要19・不要18・わからない3）での結果:

```
                                  不要を拾った     必要を止めた   拾ったうち不要
K1 目的 × 品名＋説明               11 / 18 (61%)    0 / 19         100%
K2 目的 × 品名だけ                 16 / 18 (89%)    8 / 19          67%
Jev（48件での実測、9節）           20 / 21 (95%)    0 / 23         100%
```

- 明らかに無関係な購入（天気、暗号資産、場違いの素材など）は、K1 で漏れなく拾える。ここに判断モデルは要らない。
- K1 が見逃したのは7件: clip-beach-day（動画）、music-track（動画）、playlist-placements と competitor-stats（週次レポート）、
  catering-prices（会場予約）、holiday-calendar（翻訳）、eth-ohlc-1y（ETH価格）。Jev が見逃したのは music-track（動画）の1件だけ。
  したがってモデルの上積みは6件で、種類は「範囲外・過剰・雰囲気違い・他で無料」。キーワードでは構造的に拾えない。
  この6件の対応は、Jev の見逃しが1件という集計からの推定。台帳があれば `appe-keyword-baseline` が同じ購入で並べて確かめる。
- 題材の偏り: シナリオは Claude Code が書いたので、必要な品目には目的と同じ語が入っている。K1 が必要なものを1件も止めなかったのは
  そのため。実際の購入では、語が一致しないのに必要な場面が増え、K1 は誤って確認に回す側に崩れると見込まれる（未検証）。
- 上積みの6件は、範囲外か・過剰かという主観の領域にある。表と Jev が一致したことに意味はあるが、別の人のラベルでは確かめていない。

### 評価

- 部品としては動き、キーワードより上積みがある。ただし上積みは小さく、架空のシナリオでの話。
- 最大の未確認は精度ではなく頻度: 実際のエージェントが不要な購入をどれくらいの頻度でするかを、誰も測っていない。
  決まったルートを定時に買う運用なら、ほぼ0回で、Spend Guard の価値もほぼ0になる。
- Delivery Review: 段階3の3件は、すべてコードの照合（`fields_ok`）だけで捕まっている。モデルが足したものは1件も示されていない。

### 決定（オーナー）

- 中核に据える: タスク単位の Allowance、予約・確定・解放、送信前の照合、内容のハッシュに結び付けた承認。
  いずれも、実際に起きた失敗か、起こりうると確かめた失敗に対応していて、判断モデルを使わない。
- Spend Guard は外せる部品として残す。`spend_guard.mode` は `off`（目的と売り手の説明を外部に送らない）。
  検証の記録（`validation`）は残し、再び使うときは確認モードから始める。
- 段階6〜8は着手しない。
- devnet で開いているタスクは閉じる（`npm run task -- close-all`）。鍵の扱いはオーナーが決める。
