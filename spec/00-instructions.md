- 支払いの署名や実行を、クライアント側の返り値だけで判断しない。**検証はすべてサーバー側で行う**（Worldの必須要件）

## 2. 全体構成

```text
[デモ用エージェント（TypeScript）]
  有料APIを呼ぶ → 402応答 → 支払い要件を取得
        ↓
[Countersign（サーバー側）]
  1. 固定ルール：allowlist、1件あたりの上限、ラン全体の上限、同一ルートの再購入
  2. Intercepta：payTo・トークン・支払い承認のスクリーニング
  3. （余力があれば）Jev：重複購入か、タスクに必要かの確率
        ↓
  判定：PAY / CAP / ASK_HUMAN / BLOCK
        ↓
  ASK_HUMAN → World ID for Agents で本人確認を要求
        承認 → 支払う
        拒否・期限切れ・キャンセル → 支払わない
        ↓
[追記型の台帳（JSONL、ハッシュチェーン）]
        ↓
[UI：判定のタイムライン + 承認画面]
```

### 技術構成

- Node.js 20 + TypeScript
- フロント：Next.js（スターターキットとして使用し、その旨をREADMEに記載）
- 支払い：Base Sepolia。x402の買い手側SDKを使う
- 売り手側：デモ用のx402エンドポイントを自作する（価格を変えて、少額・高額のケースを作れるようにする）
- 保存：ファイル（JSONL）。DBは使わない

## 3. 実装の順番

**この順で作ること。** 1〜4が終われば、Interceptaの賞の必須要件を満たします。5〜6でWorldの要件を満たします。

### 1. x402の往復（目標：金曜中）

- デモ用の売り手エンドポイントを作る（例：`/api/quote`、`/api/report`）。価格は設定ファイルで変えられるようにする
- 買い手のエージェントから呼び、402応答から支払い要件（金額、通貨、ネットワーク、payTo）を取り出す
- 支払いを付けて再送し、成功することを確認する
- **この時点で、支払いの署名直前に`gate.evaluate()`を呼ぶ分岐点を作っておく**

### 2. 固定ルール（目標：土曜午前）

- `config/policy.json`に置く（コードに埋め込まない）
  - `allowlist`：payToアドレス
  - `max_amount_per_payment`
  - `max_amount_per_run`
  - `ask_human_above`：この金額を超えたら人に聞く
  - `repurchase_window_minutes`：同じルートの再購入を検出する時間
- 判定結果は、理由コードの配列で返す

### 3. Interceptaの組み込み（目標：土曜午前）

署名の前に、次の3つを呼ぶ。

| 対象 | 使うAPI |
|---|---|
| payTo（支払先） | Quick Scan Address / Deep Scan Address |
| トークン（本物のUSDCか偽物か） | Scan Token |
| 支払い承認そのもの | Scan Message |

- **リスクデータはmainnet向けなので、支払いがBase Sepoliaでも、スクリーニングは実在のmainnetアドレスに対して行う。** デモ用の危険なアドレスは、Interceptaのdiscordチャンネルに固定されているものを使う
- APIの応答（判定と理由）を台帳に保存する。キーは保存しない
- 応答が返らない場合は`BLOCK`にする（安全側に倒す）。この方針をREADMEに書く

### 4. 判定の集約と台帳（目標：土曜午後）

集約の順番：

1. Interceptaが危険と判定 → `BLOCK`
2. allowlist外 → `BLOCK`
3. 1件あたりの上限超過 → `CAP`（上限額まで下げて支払う。下げられない場合は`BLOCK`）
4. ラン全体の上限超過 → `BLOCK`
5. `ask_human_above`を超える金額、または同一ルートの再購入 → `ASK_HUMAN`
6. それ以外 → `PAY`

台帳（`data/ledger.jsonl`）に追記するイベント：

- `payment_candidate`（402応答を受けた時点）
- `screening_result`（Interceptaの判定）
- `gate_decision`（最終判定と理由コード）
- `human_verification`（要求・結果）
- `payment_result`（成功・失敗・未実行）

各行に`event_id`、`decision_id`、`occurred_at`、`previous_event_hash`、`event_hash`を含める。既存の行は書き換えない。

### 5. World ID for Agentsの組み込み（目標：土曜夜。ここが本命）

- `ASK_HUMAN`になったら、World ID for Agentsに本人確認を要求する
- 確認が完了するまで、支払いは実行しない
- **結果の検証はサーバー側で行う。** クライアントから返ってきた値をそのまま承認として扱わない
- 次の4つの経路をすべて実装する
  - 承認 → 支払いを実行
  - 拒否 → 支払わない
  - 期限切れ（タイムアウト） → 支払わない
  - キャンセル → 支払わない
- どの資格情報（credential）を使うかを選び、**なぜそれが必要十分なのかをREADMEに書く**。審査は「たくさん使ったか」ではなく「適切な選択をしたか」を見る

### 6. UI（目標：土曜夜）

3画面だけ作る。凝らない。

- **判定のタイムライン**：候補・スクリーニング結果・判定・結果を時系列で表示。理由コードと、Interceptaの判定理由を見せる
- **承認画面**：本人確認を求められている支払いの内容（相手、金額、用途）を表示
- **結果表示**：支払われた / 止まった / 上限まで下げて支払われた

### 7. 余力があれば

- **Jev**：重複購入か、タスクに必要かを確率で返し、`ASK_HUMAN`の判断に使う。TypeSafeのAPIキーが必要
- **ENSv2**（Sepolia）：支払先のエージェントをENS名で識別し、上限やallowlistをそのnameに紐づける。「エージェントを名前空間として扱う」と加点対象

## 4. デモのシナリオ（3本）

提出用の動画は2〜4分。次の3本を順に見せる。

| # | シナリオ | 期待する結果 |
|---|---|---|
| 1 | 安全な相手・少額 | そのまま支払われる。台帳に判定が残る |
| 2 | Interceptaが危険と判定する相手 | 支払われない。理由が画面に出る |
| 3 | 高額な支払い | World IDの本人確認を要求。**承認した場合と拒否した場合の両方を見せる** |

シナリオ2と3の「止まる」経路が、両方の賞の必須要件です。**ここを最優先で撮ってください。**

動画の注意点：

- 720p以上、2〜4分。超過・不足はアップロードで弾かれる
- 早送り禁止、AI音声禁止、スマホ撮影禁止、BGM＋テキストだけの構成は禁止
- 自己紹介は20秒以内
