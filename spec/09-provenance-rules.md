# 09 出品者の素性：判定ルールと「組」の定義（探す前に固定）

2026-10-08。Colosseum 向けの新しい案（売り手を選ぶときに、その売り手の素性を引ける x402 の API）について、
**再販と上流の組を探す前に**、判定のルールと、何を「組」と数えるかをここに固定する。組を見ながらルールを
変えないため（オーナーの指示：ルールを固定 → 組を探す → 金額）。このファイルのコミットが、探す前に決めた記録になる。

前提（オーナーと合意済み）:
- 照会は、売り手を選ぶとき（開発者が候補を比べる場面、または最初に経路を決める場面）に、売り手ごとに1回。
  購入の直前に毎回引く前提にはしない。
- 出力は判決ではなく証拠: 観測した事実、その根拠、確からしさ。実在の会社を「再販」と断定しない。
- 組が見つからなければ、そこで止めて相談する。締切に合わせて無理に形を作らない。

## データ

- `kato9292929/endpoint` の commit `83e33d7`（2026-10-07 の日次取得）の `data/endpoints_full.json.gz`
  （generated_at 2026-10-07T13:22:58Z、131,675 件）。
- 判定は同 commit の `scripts/brands.mjs` をそのまま使う（`BRANDS` / `HOSTING` / `GATEWAYS`、
  `firstPartyBrand` / `borrowedBrand` / `gatewayOf`）。一覧に会社を足したり、ルールを直したりはしない。

## 対象にする記録（両側とも）

1. `price` があり、`currency` が `USDC`、`unit` が `per-call`、`amount` が 0 より大きい。
2. `last_seen` が generated_at から 14 日以内。
3. `networks` が空でない。

## 分類（ブランド B ごと）

- **自社出品 F(B)**: `firstPartyBrand(host) == B`（B が管理するドメインの下のホスト。ホスティングとゲートウェイは除く）。
- **他社名を掲げた出品 R(B)**: 自社出品でない記録のうち、次のどれか。
  - `borrowedBrand(host) == B`（B の名前がホスト名に入っているが、B のドメインではない）
  - ゲートウェイのホスト（`gatewayOf(host)` が非 null）で、`name` か `description` に B の表示名が単語として出る
  - それ以外のホストで、`name` か `description` に B の表示名が単語として出る
  （表示名は `BRANDS` の値。大文字小文字を区別せず、前後が英数字でない位置での一致。）

これは「名前を掲げている」という観測であって、「再販である」という判定ではない。出力でもそう書く。

## 組の定義

組 = (R, F)。次をすべて満たすもの。

1. 同じブランド B。
2. ネットワークが重なる（`R.networks ∩ F.networks` が空でない）: 同じ買い手が両方に払える。
3. 同じ機能: URL パスの最後の空でない区切りを小文字にし、英数字以外を除いたもの（機能キー）が一致する。
4. F の方が安い: `F.price.amount < R.price.amount`。

機能キーが一致しない「同じブランドだが機能が違う」候補は、別に数えて報告するだけで、組には数えない。

## 手による確認（数えるのは確認済みのものだけ）

3 を満たした候補を1件ずつ確かめ、次がすべて言えたものだけを「確認済みの組」とする。

- 両方が、支払いなしで 402 の応答を返す（今も x402 で買える）。
- 402 の応答か目録の説明から、同じ種類のデータ（例: 同じ銘柄の現在価格）を返すと読める。
- 根拠（両方の URL、説明、価格、確認した日時）を残す。

## 金額

確認済みの組ごとに:
- 1回あたりの差 = R の価格 − F の価格、倍率 = R ÷ F。
- 1か月あたりの差 = 1回あたりの差 × 600（1日20回 × 30日。AA の購入回数に合わせた仮定）。

## 止める条件

- 確認済みの組が 0 件なら、デモの形を作らずに止めて相談する。
- 組はあっても、1か月あたりの差が照会の価格を下回るなら、採算が立たないことをそのまま報告する。

# 09-2 x402 の観測データ：自己取引の判定にカタログ情報が何を足すか（基準を先に固定、2026-10-08）

オーナーの指示書（2026-10-08「x402 の観測データを分析側へ寄せる」）の2節。数字を見る前に、X と Y と判定の定義を固定する。

## 前提（このコミットの時点で確認したこと）

- カタログ（`kato9292929/endpoint`）は、元の情報源が持つ受取アドレス（`accepts[].payTo`）を保存していない
  （`scripts/x402-discovery.ts` は読むが、`Endpoint` に残さない）。ホストと受取アドレスの対応は、402 を自分で取るか、
  カタログ側に保存を依頼するまで作れない。カタログの進め方には踏み込まず、必要なら依頼の形で書く。
- TRM の分類はアドレス単位では公開されていない。比べる相手は「TRM が公表している方法を、こちらが読んで再現したもの」になる。
  TRM の結果そのものとの比較ではないことを、結果にも必ず書く。
- チェーン上の送金データ（Base・Solana）は、索引サービスへの接続が要る。この環境からは接続できない。

## 対象

2026年9月の Base と Solana の USDC 送金のうち、受取先が「カタログの 402 応答に出る payTo」の集合 R に入るもの。

## 判定の定義（固定）

- **集中（TRM の方法の再現）:** 受取アドレス r について、(a) 上位3つの支払元が r の受取額の 80% 以上、または
  (b) r の支払元のどれかが R に入っているか、同じ月に r から受け取っている（往復）。
- **分類できない:** 同じ月の受取が10件未満の r。
- **カタログ側の情報（ホストの区分）:** r を payTo に掲げるホストを、`scripts/brands.mjs`（endpoint@83e33d7、変更しない）で
  自社出品 / ゲートウェイ / 他社名を掲げた出品 / どれでもない、に分ける。1つの r に紐づくホスト数も数える。
- **分類が変わる:** 集中と判定された r のうち、ホストが自社出品であるもの、またはゲートウェイで紐づくホストが5件以上のもの
  （どちらも、少数の支払元から多く受け取っても商取引として説明がつく）。

## 成立の基準（数字を見る前に固定）

- **X = 10%:** 集中と判定された受取額のうち、カタログ側の情報で「分類が変わる」ものが 10% 以上。
- **Y = 25%:** 分類できない受取額のうち、カタログ側の情報でホストの区分が付くもの（「どれでもない」以外）が 25% 以上。
- どちらかを満たせば成立。どちらも満たさなければ不成立（TRM の後追い）。
- 受取額（USDC）で判定し、件数も併記する。データが揃わず一方でも測れなければ、その項目は「測定できず」とする。
